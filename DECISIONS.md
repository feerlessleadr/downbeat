# DECISIONS (append-only, newest at the bottom)

### 2026-11-26, Start Downbeat: a simple Music Assistant client
- **Context**: Owner wants an Android app for Music Assistant, named Downbeat, that may borrow functionality from other open-source Music Assistant apps but is simple and sleek to use.
- **Options considered**: Backend = Music Assistant server only, Emby music library only, or both. Scope = remote control only versus also playing audio on the phone.
- **Decision**: Backend is the Music Assistant server only. v1 = Now Playing + queue, browse + search library, multi-room / player groups. Phone-as-player, provider setup and server admin are out of v1. Stack: Kotlin, Jetpack Compose (Material 3), minSdk 26, like the owner's other apps. Standalone, public repo feerlessleadr/downbeat (not created yet).
- **Rationale**: A focused remote is what "simple and sleek" asks for; Emby is already covered by Embidextrous and mixing sources would add scope. Same stack reuses known tooling.
- **Impact**: New folder `C:\dev\downbeat`; WORKSPACE.md updated. No change to other projects. External dependency only: the Music Assistant server.

### 2026-11-26, Connection layer design
- **Context**: First real code: the Music Assistant websocket client.
- **Decision**: One single-use `MaClient` per session (reconnect = new client, decided by the caller). Models keep enums as strings and give every field a default so a newer server cannot break parsing. Event data stays raw JSON until payload shapes are verified. The client accepts several error-field names because the real error reply has not been captured. Auth rejection is a separate state (`AuthFailed`) from a dropped connection so the UI can ask for a new sign-in instead of retrying forever. Server URL is turned into `<typed address>/ws` and OkHttp upgrades it, so https stays https.
- **Rationale**: Unverified parts of the protocol are isolated and tolerant; tests use a scripted fake server shaped like the verified protocol.
- **Impact**: `app/.../ma/` and its tests; sample script extended to capture the missing facts.

### 2026-11-26, Real-sample tests and null results
- **Context**: Second sample run showed `error_code` is numeric, unknown player ids give `result: null` instead of an error, token creation returns a plain string, and only `player_updated` events were captured.
- **Decision**: Keep error codes as strings in `MaException` (numeric codes are converted). Treat a null result as a normal answer ("not found"), not an exception. Added `RealSamplesTest`, which decodes the owner's local sample files when `DOWNBEAT_SAMPLES` is set and skips otherwise, so real data never enters the repo. Until queue events are seen, the app re-reads the affected queue after player events.
- **Rationale**: Tests against real shapes catch model drift without committing device data.
- **Impact**: `MaClientTest` (two new tests), `RealSamplesTest`, docs.

### 2026-11-26, Sign-in, token storage and connection ownership
- **Context**: Needed a way to sign in without ever storing the password, and one place that owns the live connection.
- **Options considered**: Login over the websocket versus a plain HTTPS POST; keep the 30-day login token versus swap it for a 1-year long-lived token; androidx security-crypto versus the Android Keystore directly; a ViewModel per screen versus one app-wide repository.
- **Decision**: Login is HTTPS `POST /auth/login` (the server documents it in openapi.json). After login the app opens one websocket, calls `auth/token/create` for a long-lived token, and stores only that (falling back to the login token if creation fails). The token is encrypted with an AES-GCM key in the Android Keystore (no deprecated security-crypto library). http addresses are refused (`requireHttps`, and cleartext is also off in the manifest). One `MusicRepository` owns one `MaClient` at a time, retries with 1 to 30 second backoff, and signs the user out when the server refuses the token. Sign-out forgets the token locally but does not revoke it on the server yet.
- **Rationale**: The password exists only in one request body. A long-lived token survives a month of not opening the app. One owner of the connection keeps screens simple and reconnect logic in one tested place.
- **Impact**: `data/`, `ma/MaAuth.kt`, `ui/`, manifest (`DownbeatApp`). Revoking the token on sign-out is a to-do.

### 2026-11-26, Client must answer a server-initiated close
- **Context**: A repository test showed no reconnect after the server dropped the socket.
- **Decision**: `MaClient` answers `onClosing` and reports Disconnected immediately.
- **Rationale**: OkHttp only calls `onClosed` after the client answers, so a server restart would have left the app showing stale rooms forever.
- **Impact**: `ma/MaClient.kt` plus a test.

### 2026-11-26, Playing screen: leader resolution, tap rules, controls
- **Context**: Turning the approved rooms design into behaviour.
- **Decision**: Pure functions in `RoomLogic` decide everything about rooms. The leader is `active_group`, else `synced_to`, else the chosen room. A tap on an unticked room adds it to the set only if both are single players with `set_members` and the room is in the leader's `can_group_with`; otherwise it switches to that room (and moves the queue with `transfer` if something is playing). Static group members are locked. The leader of a sync set cannot be unticked (untick the others); a lone room cannot be unticked. Default room: one that is playing, else the first single room, never a static group by surprise. Buttons are shown only if the leader's `supported_features` allow them. Position is elapsed time plus time since it was recorded, while playing. Group volume is used when several rooms play together. Transport uses the leader's queue id. Artwork uses Coil, with the token added only for the server's own host.
- **Rationale**: Keeps the "one list, one gesture" promise while respecting what the server verifiably allows; everything testable without a phone.
- **Impact**: `data/RoomLogic.kt`, `NowPlaying.kt`, `PlaybackController.kt`, `AppPrefs.kt`, `ui/*`, new dependencies `coil-compose` and `coil-network-okhttp` 3.3.0. Open: if the server needs a different image auth, adjust `DownbeatApp.newImageLoader`.

### 2026-11-27, Fixes from the first phone test of the Playing screen
- **Context**: Owner's test showed: a TV chosen as the default room, no next/previous buttons, seek bar not draggable, shuffle icon never changing, and 10 to 15 s to reconnect after the screen was off.
- **Options considered**: Keep gating next/previous/seek on `supported_features` (rejected: the player lists none of them yet the web UI offers them, because they are queue commands the server runs). Wait for the 30 s websocket ping to notice a dead socket (rejected: too slow).
- **Decision**: Always show next, previous and seek. Default room prefers a playing room, then a single room that can pause (a real speaker), then any single room. Re-read the queue right after shuffle and repeat. Add `MusicRepository.onForeground()`: on activity start and when a network becomes available it skips the reconnect wait, or when online checks the connection with a 3 s request and reconnects at once if it fails.
- **Rationale**: Queue state events were not seen, so the app cannot rely on them; a socket that slept with the screen off can look alive.
- **Impact**: `NowPlaying.kt`, `RoomLogic.kt`, `PlaybackController.kt`, `MusicRepository.kt`, `MainActivity.kt`, `DownbeatApp.kt` (network callback). Tests added for the foreground nudge and the default room.

### 2026-11-27, Seek position comes from the queue
- **Context**: After a seek on the phone, the bar snapped to the start and stayed out of sync with the web UI until the next song. The web UI reads the queue's `elapsed_time`; the app preferred the player's own clock, which can restart after the device re-opens its stream. Cause not confirmed against real data.
- **Options considered**: Keep the player clock and only hold the dragged value (hides it, does not fix drift); read the queue only.
- **Decision**: Position uses the queue's `elapsed_time` and `elapsed_time_last_updated` when present, else the player's. After a seek the queue is re-read at 1 s and 3 s. The repository re-reads the queue of every playing room every 10 s (`queuePollMs`). The screen keeps the dropped position for 5 s after a release.
- **Rationale**: Matches the web UI and cannot drift for long even without queue events.
- **Impact**: `NowPlaying.kt`, `PlaybackController.kt`, `MusicRepository.kt`, `PlayingScreen.kt`. If the bar is still wrong after this, capture the player and queue elapsed fields after a seek.

### 2026-11-27, M2: power, first-run room picker, token revoke on sign-out

### 2026-11-27, Themes: base colours plus an accent that follows the music
- **Context**: Owner asked how "match the music" chose its colour (a small patch of green on an album won), whether the colours should return to normal when playback stops, and suggested a base theme with only the highlight colours following the music.
- **Findings**: The first version averaged pixels weighted by saturation and lightness fit, so small vivid patches outweighed large muted areas. Material's own method (material-color-utilities `Score`) counts how much of the picture each hue covers first (population share in 30 degree windows, hues below 1 percent and colours of chroma below 5 dropped) and gives chroma only a small weight (0.1 below a target of 48, 0.3 above), then builds the theme from that one source colour, keeping neutral surfaces stable.
- **Options considered**: Adding Material Color Utilities as a dependency (rejected: not needed for this; the ranking is small enough to reimplement and test); keeping "match the music" as a whole palette (rejected by the owner's idea and Material's guidance of stable neutrals).
- **Decision**: (1) Cover colour: pixels are grouped by hue; a hue's score is 0.7 times its share of the picture (within a 30 degree window, hues with 1 percent or less ignored, near-grey pixels ignored) plus a small chroma term; the best hue's average colour is the seed; a picture with no colourful hue gives its average (a grey accent). (2) Settings, Appearance: Mode; "Follow the music" switch (accent only); base colours (seven named colours or Phone colours). The base colours make the surfaces, text and outlines and never change with the music. With the switch on, the primary, secondary and tertiary roles (buttons, highlights, selected tabs, the player bar's progress) take the cover's colour, fading over 0.9 s between songs. When playback stops (not paused) they fade back to the base accent after 2.5 s (so the gap between songs does not flash). The Playing screen's dark scheme follows the same rules. Settings saved by the first version with the palette "music" become the switch on with the default base. Phone colours work as a base too.
- **Rationale**: Population first matches how people read a cover; stable surfaces keep the app readable and calm.
- **Impact**: `ThemeSettings.kt` (`dominantColor`, `withAccent`, `accentFollowsMusic`), `AppPrefs`, `MusicRepository`, `AppTheme.kt`, `AppearanceScreen.kt`, `ThemeTest`. Unverified on the phone: that the chosen colours look right across the owner's albums, and the fade back when stopped. Sources used for the Material method: Material Color Utilities documentation and its Score implementations (Dart, Rust and TypeScript ports; constants taken from the ports, which may differ by version).

- **Decision**: Four slices, each tested on the phone: (1) read-only Server screen (built now), (2) tasks, library sync and token actions, (3) user management, (4) player settings. Server-wide core settings, remote access, DSP, dashboards and party mode stay out of M7 unless asked. Slice 1: Settings gets a "Server" row for administrators (same check as providers); the screen shows This server (name, version, status, add-on or standalone, remote access; the server's addresses are never read), Background tasks (status in the server's word, progress, last and next run, last error), Users (name, role, disabled, joined), Access tokens (name, kind, created, last used, expires; this phone's token marked and listed first; token hashes never read) and the Application log on demand (last 200 lines, selectable). Each part loads on its own so one refused read does not blank the screen. Dates are accepted as seconds, milliseconds or ISO text.
- **Impact**: `docs/server-admin-research.md`, `Models.kt` (`ServerAbout`, `AdminUser`, `BackgroundTask`, token dates), `MaApi` (`aboutServer`, `adminUsers`, `backgroundTasks`, `serverLog`), `data/ServerAdmin.kt`, `MusicRepository.thisTokenName`, `ui/ServerScreen.kt`, `SettingsScreen`, `AppRoot`; 7 tests. Unverified on the real server: the shapes of every answer and whether the owner's account may read all of them.
